# PCI DSS Encryption Architecture Guide

## Overview
This document explains a structured encryption model commonly used in banking and payment environments to protect PAN (Primary Account Number) and other sensitive data. It covers:

- Symmetric key hierarchy (DEK / KEK)
- HSM-backed encryption
- Tokenization
- Key rotation
- SQL Server Always Encrypted vs HSM tokenization
- PCI DSS aligned operational controls

---

## Core Key Concepts

### Data Encryption Key (DEK)
Used to encrypt the actual sensitive data.

Examples:
- PAN
n- Personal data
- Files
- Database columns

Typically uses AES-256 or equivalent symmetric encryption.

### Key Encryption Key (KEK)
Used to encrypt (wrap) the DEK.

Also known as:
- Master Key
- Wrapping Key
- Key Protecting Key

### Root Key / LMK
Stored only inside the HSM.
Used to protect higher-level keys.

---

## Recommended Key Hierarchy

```text
LMK / Root Key (inside HSM only)
        ↓
KEK / Master Key
        ↓
DEK / Data Key
        ↓
Encrypted PAN / Sensitive Data
```

## PAN Encryption Flow

### Step 1: Receive PAN
```text
4111 1111 1111 1111
```

### Step 2: Encrypt PAN with DEK
```text
CipherPAN = AES-GCM(PAN, DEK)
```

### Step 3: Protect DEK with KEK
```text
WrappedDEK = Encrypt(DEK, KEK)
```

### Step 4: Store in Database

| Token | Encrypted PAN | Wrapped DEK ID | Last4 |
|------|----------------|----------------|------|
| TKN123 | ...cipher... | KEY_2026_Q2 | 1111 |

---

## PAN Decryption Flow

### Step 1: Receive Decrypt Request
Authorised system presents a token or record reference requiring PAN retrieval.
```text
Request: decrypt(TKN123)
```

### Step 2: Look Up Wrapped DEK
Retrieve the Wrapped DEK ID associated with the record from the database.
```text
WrappedDEK = DB.lookup(TKN123) → KEY_2026_Q2
```

### Step 3: Unwrap DEK using KEK (inside HSM)
The KEK never leaves the HSM. Unwrapping happens entirely within the HSM boundary.
```text
DEK = HSM.Decrypt(WrappedDEK, KEK)
```

### Step 4: Decrypt PAN using DEK
```text
PAN = AES-GCM-Decrypt(CipherPAN, DEK)
→ 4111 1111 1111 1111
```

### Step 5: Return PAN to Authorised Caller
PAN is returned only over an encrypted channel (TLS). It is never logged or persisted.
```text
Response (over TLS): 4111 1111 1111 1111
```

### Decryption Flow Summary

```text
Token / Record Reference
        ↓
  DB Lookup → CipherPAN + WrappedDEK ID
        ↓
  HSM: Unwrap DEK using KEK
        ↓
  Decrypt CipherPAN using DEK
        ↓
  PAN returned over TLS to authorised caller
```

## Tokenization Model

Replace PAN with a token for internal usage.

```text
4111111111111111 -> TKN123
```

Internal systems use the token instead of PAN.

### Benefits
- Reduced PCI scope
- Lower breach impact
- Easier downstream integrations
- Better data minimization

---

## Key Rotation Model

### Example Schedule
- Quarterly
- Semiannual
- Annual (depends on policy/risk)

### Rotation Steps
1. Generate new DEK inside HSM.
2. Wrap new DEK under KEK.
3. Use new DEK for new transactions.
4. Keep old DEKs for decrypting historical data.
5. Optional background re-encryption of old records.

### Example
- KEY_2026_Q1 (old)
- KEY_2026_Q2 (new active)

## HSM Operational Controls

### Recommended Controls
- Keys generated inside HSM
- Non-exportable master keys
- Dual control for ceremonies
- Split knowledge for key components
- Strong authentication for operators
- Full audit logging
- HA / clustered HSM deployment

- Thales

## SQL Server Always Encrypted vs HSM Tokenization

| Topic | SQL Server Always Encrypted | HSM Tokenization |
|---|---|---|
| Goal | Protect DB-side visibility | Centralize PAN protection |
| PAN in Apps | Often yes | Usually no |
| Scope Reduction | Moderate | Strong |
| Multi-system Reuse | Limited | Strong |
| Complexity | Lower | Higher |
| Strategic Fit for Banks | Tactical | Strategic |

## PCI DSS Aligned Good Practices

### Never Store
- Plain PAN in logs
- Keys in source code
- Unencrypted exports
- Full PAN in screenshots

### Restrict Access
- Least privilege
- Need-to-know access
- Segregation of duties
- Approval workflows for decrypt access

### Monitor
- All decrypt requests logged
- Alert on spikes/anomalies
- Regular access reviews

---

## Practical Decision Guidance

### Use Always Encrypted When
- Existing SQL Server application needs faster uplift
- Main risk is DBA access to PAN
- Limited number of consuming apps

### Use HSM Tokenization When
- Multiple channels process PAN
- PCI scope reduction is priority
- Enterprise-wide card platform modernization planned

### Use Hybrid When
- Need tactical short-term control + long-term strategic platform

---

## Executive Summary

Use DEKs to protect data, KEKs to protect DEKs, HSMs to protect keys, and tokens to reduce exposure.

For most banks, tokenization with HSM-backed key management is the strategic end-state.
